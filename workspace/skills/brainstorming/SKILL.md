# Brainstorming - 将想法转化为设计

帮助通过自然的协作对话将想法转化为完整的设计和规范。

首先了解当前项目背景，然后一次一个地问问题来完善想法。一旦理解了你想要构建的内容，呈现设计方案并获得用户批准。

<HARD-GATE>
在呈现设计方案并获得用户批准之前，**禁止**调用任何实现技能、编写任何代码、搭建任何项目或采取任何实现行动。这适用于每个项目，无论其复杂程度如何。
</HARD-GATE>

## 反模式："这太简单了，不需要设计"

每个项目都要经过这个过程。待办事项列表、单功能工具、配置更改——所有这些。"简单"项目是未经检验的假设导致最多浪费工作的地方。设计可以很短（对于真正简单的项目可以是几句话），但你必须呈现它并获得批准。

## 流程清单

你必须按顺序完成以下每个任务：

1. **探索项目背景** — 检查文件、文档、最近的提交
2. **提出可视化伴侣**（如果主题涉及可视化问题）— 这是单独的消息，不要与澄清问题合并。参见下面的可视化伴侣部分。
3. **提出澄清性问题** — 一次一个，理解目的/限制/成功标准
4. **提出 2-3 种方案** — 包含权衡和你的推荐
5. **呈现设计方案** — 按复杂性缩放各部分，在每个部分后获得用户批准
6. **编写设计文档** — 保存到 `docs/plans/YYYY-MM-DD-<主题>-design.md` 并提交
7. **过渡到实现** — 创建详细的实施计划

## 探索流程图

```
项目背景 → 有可视化问题？ → (是) 提供可视化伴侣 → 提问澄清问题
                ↓(否)
                提问澄清问题 → 提出方案 → 呈现设计 → 用户批准？
                                                                    ↓
                                                            (否)修改设计
                                                                ↓(是)
                                                         编写设计文档 → 过渡到实施
```

**最终状态是过渡到实施计划。** 不要调用其他实现技能。

## 详细流程

### 理解想法

- 首先检查当前项目状态（文件、文档、最近提交）
- 在问详细问题之前，评估范围：如果请求描述多个独立子系统（例如"构建一个包含聊天、文件存储、计费和分析的平台"），立即标记这一点。不要花时间完善一个需要首先分解的项目细节。
- 如果项目太大无法单个 spec 分解，帮助用户分解为子项目：独立的 pieces 是什么？它们如何关联？应该按什么顺序构建？然后通过正常设计流程对第一个子项目进行头脑风暴。每个子项目都有自己的 spec → 计划 → 实现周期。
- 对于适当规模的项目，一次一个地问问题来完善想法
- 尽可能使用多项选择问题，但开放性问题也可以
- 每条消息只问一个问题——如果一个主题需要更多探索，分为多个问题
- 重点理解：目的、限制、成功标准

### 探索方案

- 提出 2-3 种不同方案，包含权衡
- 对话式地呈现选项，包含你的推荐和理由
- 首先提出你的推荐选项并解释为什么

### 呈现设计

- 一旦你相信自己理解了要构建的内容，就呈现设计
- 根据复杂性缩放每个部分：简单的几句话，微妙的 up to 200-300 字
- 在每个部分后询问是否看起来正确
- 覆盖：架构、组件、数据流、错误处理、测试
- 准备好回去澄清一些不合理的地方

### 设计隔离和清晰性

- 将系统分解为更小的单元，每个单元有一个清晰的目的，通过明确定义的接口通信，可以独立理解和测试
- 对于每个单元，你应该能够回答：它做什么？你怎么使用它？它依赖什么？
- 有人能在不阅读内部代码的情况下理解一个单元做什么吗？你能在不破坏使用者的情况下改变内部代码吗？如果不能，边界需要改进
- 更小、边界更好的单元也更容易与你合作——你能够更好地推理可以一次性掌握上下文的代码，当文件专注于单一职责时你的编辑也更可靠。当一个文件变大时，这通常是一个信号，表明它做得太多了

### 在现有代码库中工作

- 在提出更改之前探索当前结构。遵循现有模式。
- 如果现有代码有问题影响工作（例如，一个变得太大的文件、模糊的边界、纠缠的职责），将针对性的改进作为设计的一部分——就像一个好的开发者在工作的代码中改进一样。
- 不要提出无关的重构。专注于为当前目标服务的的东西。

## 设计之后

### 文档

- 将经过验证的设计（规格）写入 `docs/plans/YYYY-MM-DD-<主题>-design.md`
- （用户对 spec 位置的偏好优先于此默认位置）
- 将设计文档提交到 git

### 实现

- 创建详细的实施计划
- 不要调用其他技能。实施计划是下一步。

## 关键原则

- **一次只问一个问题** - 不要用多个问题淹没用户
- **优先多项选择** - 比开放性问题更容易回答
- **YAGNI 严格执行** - 从所有设计中删除不必要的功能
- **探索替代方案** - 在确定之前始终提出 2-3 种方法
- **增量验证** - 呈现设计，获得批准后再继续
- **保持灵活** - 当某些事情不合理时回去澄清

## 可视化伴侣（可选）

浏览器伴侣，用于在头脑风暴期间显示线框图、图表和可视化选项。作为工具提供——不是一种模式。接受伴侣意味着它可用于受益于视觉处理的问题；这并不意味着每个问题都必须通过浏览器。

**提供伴侣：** 当你预期即将到来的问题涉及可视化内容（线框图、布局、图表）时，提供一次以获得同意：
> "我们正在处理的一些内容如果能在网页上展示可能会更容易解释。我可以随着我们的进展整理线框图、图表、比较和其他视觉效果。你想试试吗？（需要打开本地 URL）"

**这个提议必须是它自己的消息。** 不要将其与澄清问题、上下文摘要或任何其他内容合并。消息应仅包含上述提议内容，不要包含其他内容。在继续之前等待用户的回复。如果他们拒绝，继续纯文本头脑风暴。

**每个问题的决策：** 即使用户接受了，也要为**每个问题**决定是使用浏览器还是终端。测试：**用户通过看到它比阅读它更好地理解吗？**

- **使用浏览器** 内容是视觉的 — 线框图、布局比较、架构图表、并排视觉设计
- **使用终端** 内容是文本的 — 需求问题、概念选择、权衡列表、A/B/C/D 文本选项、范围决策

关于 UI 主题的问题不自动是视觉问题。"这个背景色应该是什么颜色"是视觉问题 — 使用浏览器。"这个功能在这个上下文中的目的是什么"是概念问题 — 使用终端。
