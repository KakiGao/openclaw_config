# 系统性调试 (Systematic Debugging)

## 概述

随机的修复浪费时间，还会引入新的 bug。快速补丁只会掩盖潜在问题。

**核心原则：** 在尝试修复之前**必须**找到根本原因。仅仅修复症状是失败的做法。

**违反这个流程的形式，就等于违反调试的精神。**

## 铁律

```
未经根本原因调查，禁止提出任何修复方案
```

如果你没有完成第一阶段，就不能提出修复方案。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**特别要在以下情况使用：**
- 时间紧迫时（紧急情况容易让人想走捷径）
- "就一个 quick fix" 看起来很明显时
- 你已经尝试过多个修复方案
-之前的修复没有起作用
- 你不完全理解这个问题

**不要跳过当：**
- 问题看起来很简单（简单的 bug 也有根本原因）
- 你很着急（匆忙注定要返工）
- 经理想要马上修好（系统性比盲目尝试更快）

## 四个阶段

你必须完成每个阶段后才能进入下一个。

### 阶段 1：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完全阅读堆栈跟踪
   - 记录行号、文件路径、错误代码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 每次都发生吗？
   - 如果无法复现 → 收集更多数据，不要猜测

3. **检查最近的变更**
   - 什么变更可能导致这个问题？
   - Git diff、最近的提交
   - 新增依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → build → signing, API → service → database）：**

   **在提出修复之前，添加诊断工具：**
   ```
   对于每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每层的状态

   运行一次以收集证据显示在哪里出问题
   然后分析证据以识别失败的组件
   然后调查该特定组件
   ```

5. **追踪数据流**

   **当错误在调用栈深处时：**

   - 坏值从哪里来的？
   - 是什么调用时传入了坏值？
   - 一直追溯直到找到源头
   - 在源头修复，而不是症状处

### 阶段 2：模式分析

**修复之前找到模式：**

1. **找到工作的例子**
   - 在同一代码库中找到类似工作的代码
   - 什么与坏的一样？

2. **对比参考实现**
   - 如果正在实现某个模式，完全阅读参考实现
   - 不要略读 — 每行都要读
   - 在应用之前完全理解模式

3. **识别差异**
   - 工作和坏的区别是什么？
   - 列出每个差异，无论多小
   - 不要假设"那个不重要"

4. **理解依赖**
   - 这个还需要什么其他组件？
   - 什么设置、配置、环境？
   - 它做什么假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清楚地说明："我认为 X 是根本原因，因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做最小的可能改变来测试假设
   - 一次一个变量
   - 不要同时修复多个东西

3. **在继续之前验证**
   - 成功了吗？ → 阶段 4
   - 没成功？形成新假设
   - 不要在上面继续添加修复

4. **当你不明白时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 继续研究

### 阶段 4：实现

**修复根本原因，而不是症状：**

1. **创建失败的测试用例**
   - 最简单的复现
   - 如果可以自动化测试
   - 如果没有框架就一次性测试脚本
   - 修复前必须有测试用例

2. **实现单一修复**
   - 解决已识别的根本原因
   - 一次一个更改
   - 没有"既然来了"的改进
   - 没有捆绑的重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有其他测试坏掉？
   - 问题真的解决了？

4. **如果修复不起作用**
   - 停止
   - 数一下：你尝试了多少个修复？
   - 如果 < 3：回到阶段 1，用新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（见下面第 5 步）**
   - 不要在没有架构讨论的情况下尝试修复 #4

5. **如果 3+ 修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每个修复都在不同地方暴露新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实现
   - 每个修复在其他地方产生新症状

   **停止并质疑基础：**
   - 这个模式根本上是合理的吗？
   - 我们是不是"纯粹因为惯性而坚持"？
   - 我们应该重构架构还是继续修复症状？

   **在尝试更多修复之前与你的伙伴讨论**

## 红线 - 停止并遵循流程

如果你发现自己想到：
- "先快速修复，以后再调查"
- "就试着改 X，看看能不能工作"
- "加多个更改，运行测试"
- "跳过测试，我手动验证"
- "可能是 X，让我修那个"
- "我不完全理解但这可能能工作"
- "模式说 X 但我会不同的方式适应"
- "主要问题是：[列出修复，没有调查]"
- 在追踪数据流之前提出解决方案
- **"再试一次修复"（当已经尝试 2+ 次）**
- **每个修复在不同地方暴露新问题**

**所有这些意味着：停止。回到阶段 1。**

**如果 3+ 修复失败：** 质疑架构（见阶段 4.5）

## 常见借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根本原因。流程对简单 bug 很快。 |
| "紧急，没时间走流程" | 系统性调试比猜测尝试更快。 |
| "先试试这个，然后调查" | 第一次修复设置模式。从一开始就做对。 |
| "确认修复有效后我会写测试" | 未测试的修复不会持久。测试优先证明它。 |
| "一次修复多个节省时间" | 无法隔离什么有效。导致新 bug。 |
| "参考太长了，我会适应模式" | 部分理解保证 bug。完全阅读它。 |
| "我看到问题了，让我修复" | 看到症状 ≠ 理解根本原因。 |
| "再试一次修复"（2+ 次后）| 3+ 次失败 = 架构问题。质疑模式，不要再修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|----------|----------|
| **1. 根本原因** | 读错误、复现、检查变更、收集证据 | 理解什么和为什么 |
| **2. 模式** | 找工作的例子、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或新假设 |
| **4. 实现** | 创建测试、修复、验证 | Bug 解决，测试通过 |

## 当流程显示"没有根本原因"

如果系统性调查表明问题真的是环境的、时间依赖的或外部的：

1. 你已经完成了流程
2. 记录你调查了什么
3. 实现适当的处理（重试、超时、错误消息）
4. 为未来调查添加监控/日志

**但是：** "没有根本原因"的情况 95% 是不完整的调查。
